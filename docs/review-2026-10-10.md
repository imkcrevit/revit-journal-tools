# 审查报告与修改计划（2026-10-10）

审查对象：`revit-journal-tools`，提交`60499be`（2026-10-09，"feat: add paragraph CLI viewer and add-in browsing"）。审查目标：读取速度、更符合Revit实际使用场景的工作逻辑、Windows适配。本次只审查和测量，没有修改仓库中的任何代码；修改由后续执行者按本文"修改计划"实施。

审查方式：通读`src/`全部模块、`docs/`、`tests/`；在本机（Windows 10 19045、Python 3.12.10、SQLite 3.49.1、系统代码页cp936）用本机真实Revit Journal做只读测量；两个性能方案做了仓库外原型验证。测量脚本的要点见附录，可按附录重建。

## 1. 结论摘要

1. **中文Windows上默认模式不可用。** 本机113个真实Journal文件中104个无法按严格UTF-8解码；13个主Journal连cp936也解不开，但全部可按gb18030解码。工具默认`--encoding auto`只做BOM识别后严格UTF-8，普通用户第一次运行就会得到"无法解码"。这是P0。
2. **读取速度有确定的提升路径。** 扫描2.2–3.1MB/s，92%时间在正则；建索引1.1–1.8MB/s（约1.5万行/秒），Python分类/分块占~60%、SQLite写入占~30%。原型证明：规则字面量门控可使扫描提速4.6倍且结果完全一致；合并大正则无效（0.9x），执行者不要走这条路。
3. **工作逻辑尚未贴合Revit排查场景。** 真实场景是"Revit刚崩了/正在卡，打开最新一次会话，先看有没有正常结束、最后在做什么、许可和插件有没有问题"。当前：不会自动找Journal目录，列表按路径升序（最旧在前，0字节`dump.0001.txt`排第一），没有"是否正常退出"（本机56个会话里19个没有结束标记），没有会话摘要和阶段，关键的Revit标记（许可错误、模型打开失败、LocalDB/钢连接、对话框）没有规则，而现有"错误"分类里大量是Revit普通建模警告（"错误: 不满足约束"）。
4. Windows适配：107项测试在本机2项失败（系统代理改写Host头；测试未关闭SQLite连接），TUI未在原生Windows验收，缓存默认落在当前目录。

## 3. 发现清单

编号用于修改计划引用。P0＝不改就无法在目标场景使用；P1＝明显影响效果或速度；P2＝改进。

### A. 编码与读取

**J1（P0）默认编码在中文Windows不可用。** `reader.py:47-58`：无BOM即严格UTF-8。证据见2.1。建议：`auto`改为逐文件决定——BOM→严格UTF-8→系统ANSI代码页的超集（cp936→gb18030；cp1252保持；其他locale按`locale.getpreferredencoding()`映射）；报告与索引记录`encoding_detected`和`encoding_fallback`。保留"不静默替换坏字节"的原则：所有候选编码都失败时，按行退化解码（`surrogateescape`或`replace`）并在该行标记`decode_degraded`，文件级记录退化行数，而不是整文件失败。验收：本机113个文件在不传`--encoding`的情况下全部可索引；报告能说明每个文件用了什么编码。

**J2（P1）一次运行只能用一个编码。** `cli.py`的`--encoding`作用于整批文件，`ViewerIndex.register`把编码写进签名。混合目录（英文系统产生的旧文件和中文系统的新文件）无法一起打开。J1实现后按文件记录即可解决；签名应记录实际使用的编码而不是请求值。

**J3（P1）无法查看正在写入的Journal。** `reader.py:132-138`在读取后比对大小/mtime，变化即整文件失败。Revit运行时journal持续增长，而"Revit正在卡死，看看它在做什么"是支持场景的一半。建议`--snapshot`模式：先复制到临时目录再索引（默认对被进程占用或本会话最新的文件启用），或按打开时的字节数截断读取并把文件标为`live`/`partial`。

**J4（P2）侧车与副本未识别。** `journal.NNNN.txt.copy.txt`与原文件逐字节相同却作为独立文件索引；0字节`dump.NNNN.txt`进入列表并排在第一；`journal.NNNN.workerN.log`没有归属到主会话；`.dmp`被正确拒绝但没有在会话里计数。建议按`journal.NNNN`前缀把主Journal、worker日志、dmp、copy归为一个会话，副本按哈希去重并只显示一次。

### B. 读取速度

**J5（P0）扫描对每行跑全部规则。** `analyzer.py:67`对每行执行全部`active_rules`，`Categorizer`有门控而`analyze`没有。方案B已验证4.6倍。实现：规则JSON新增可选字段`gate`（小写字面量数组，语义是"该规则任何命中行都必然包含其中至少一个子串"）；`Rule.match`先`lower()`一次再`any(t in lower for t in gate)`；没有`gate`的规则照旧全量匹配；`load_rules`校验`gate`非空字符串数组；为每条内置规则补`gate`，并用回归测试证明命中集合不变（用`tests`里现有正负样例+真实案例片段）。自定义规则允许不写`gate`。附录给出内置12条规则的门控建议。

**J6（P0）建索引Python侧重复工作。** 每行：`blocks.feed`执行≥8个编译正则，另有3处每次调用时才编译的正则（`blocks.py:113`、`142`、`161`）；`classify`再跑`_JOURNAL/_STARTUP/_SYSTEM/_RECORD`；`loading_payload`每行计算两次（`blocks.py:121,178`的`is_addin_start`与`loading.py:129`的`feed`各一次，共3个`re.sub`），且与是否处于加载事件无关。建议：(a)预编译全部正则；(b)增加一次"行形状解析"（时间戳、层级前缀、`Jrn.`、`API_`、正文）生成结构体，`Categorizer`、`BlockBuilder`、`LoadingEvidence`共用，不再各自剥前缀；(c)子串门控：只有`"Application" in text or "Add-in" in text`才跑`_START`，只有含`{`或`}`才算花括号深度，`content`为空走快速路径，`_METRIC/_SECTION/_STACK/_EXCEPTION`各加最便宜的子串条件；(d)`LoadingEvidence.feed`未激活时只检查起始前缀。目标：85k行的feed+classify从约4.8s降到≤1.5s。验收：`tests/test_blocks.py`、`test_loading.py`、`test_viewer.py`全部通过，且用本机真实文件比对改前改后的`blocks`表（起止行、类别、边界、addin字段）逐行一致。

**J7（P1）SQLite写入约30%。** `viewer_index.py:164-171`每5000行提交一次，FTS通过触发器逐行维护（`_SCHEMA`的`lines_insert`）。建议：构建连接使用`PRAGMA synchronous=OFF`（失败即重建，状态机已经把未完成文件当作不可用）；整文件一个事务，进度只更新`files`表的`indexed_bytes`（可用单独短事务）；FTS改为文件完成后一次性`INSERT INTO line_search(rowid, body) SELECT id, body FROM lines WHERE file_id=?`，构建期间搜索不可用（UI已有indexing态）；`executemany`批次放大到2万行。预期建索引再快1.3–1.5倍。注意保留"已完成文件先可用"的体验。

**J8（P1）多文件不并行。** 目录场景是常态（本机单个版本21个文件）。建议进程池按文件并行：子进程负责解码、分类、分块，产出行批与块批；主进程串行写库（避免多写者）。预期目录建索引接近核数线性加速。注意Windows下`multiprocessing`需`spawn`，子进程不能依赖主进程的连接对象。

**J9（P2）索引体积3.4倍。** `lines.body`保存全文。可选"偏移模式"：只存每行的字节偏移与长度，正文按需从源文件解码（源文件不变本来就是前提），FTS改为contentless（`content=''`）。体积可降到源文件的1倍以下，J3的快照模式可与之共用临时副本。改动较大，放在速度收益兑现之后。

**J10（P2）基准脚本在Windows没有内存数据。** `scripts/benchmark_streaming.py`依赖`resource`模块，Windows返回`None`。建议用`ctypes`调`GetProcessMemoryInfo`，并新增"本机真实Journal基准"入口（读取`%LOCALAPPDATA%`下的文件，结果不入库）。

### C. 工作逻辑（Revit场景）

**J11（P0）不会自动找Journal，排序与初选不符合排查习惯。** 用户要自己找到`%LOCALAPPDATA%\Autodesk\Revit\Autodesk Revit <year>\Journals`；`viewer_index.py:110`按大小升序排队、`catalog()`按路径升序，`terminal.py:133`选第一个非空文件、`app.js:82`选最小文件——都不是"最新一次会话"。建议：不传路径时枚举所有已安装版本的Journals目录（支持`--revit 2024`、`--latest`）；列表按修改时间倒序，显示日期、大小、时长、是否正常结束；默认选中最新主Journal；索引队列以选中文件优先，其余按时间倒序。

**J12（P0）没有会话级结论。** 排查第一步是"这次会话怎么结束的"。建议新增`session`层（CLI`summary`命令、TUI摘要面板、JSON的`session`节）：Build/Branch、起止时间与时长、是否有`finished recording journal file`（没有则标"未正常结束：崩溃或被结束"，本机19/56）、许可状态（`Adlsdk Error`）、打开过的文档（`openFromModelPath`、`Jrn.Command`打开类命令）、第三方Add-in数量、最后N行/最后N个操作、侧车文件清单。这些是会话级发现，应作为`session_findings`单独建模，仍标记为候选。

**J13（P1）没有阶段模型。** 建议给块附加`phase`：startup→licensing→addin_loading→document_open→interactive→shutdown，由标记驱动（`InitApplication`、`LicenseUpd`、`Starting External`、`openFromModelPath`/`Jrn.Command`、`ExitManagedInstance`/`finished recording`）。TUI和JSON支持按阶段筛选，并提供"结束前最后N个操作与对话框"视图，对应Autodesk阅读指引"结合具体操作与时间"。

**J14（P1）规则覆盖与真实频率不匹配。** 依据2.2普查新增/调整：
- `revit.license_error`（`Adlsdk Error`、`LicenseUpd(1) ... Error`），warning级，说明"许可验证失败通常早于其他现象"。
- `revit.model_open_failed`（`Load exception "`、`openFromModelPath did not complete`、`exceptionsInOnOpenDocument`），error级。
- `revit.steel_localdb`（`SQLLocalDB instance is malfunctioning`、`Steel Connections DB extension`相关异常），并在说明中指向钢连接侧车日志与RevitLocalDbFix。
- `revit.addin_conflict`（`Assembly version conflict`），info/warning级，按Add-in聚合显示而不是551行各算一次。
- 新类别"对话框"（`TaskDialog "`及其`TaskDialogResult`），这是用户实际看到的提示，是叙述会话的关键。
- `generic.error_marker`对Revit中文/英文UI提示（`错误: 不满足约束`、`Error: Can't create Railings`）降为warning并加`ui_warning`标签；它们是建模警告，不是故障。
- 会话级：`session.no_clean_exit`。
每条按`docs/rules.md`的流程配正负样例；真实片段去标识化后入`tests/fixtures/`。

**J15（P1）侧车文件未纳入。** 与会话相关的`journal.NNNN.workerN.log`、`journal.NNNN.NNNN.dmp`（只计数与大小）、CER的`cer.log`、钢连接的`%ProgramData%\Autodesk\Revit Steel Connections <year>\<lang>\DatabaseConnectionErrors.log`应在会话摘要中列出、按时间与会话对齐并可打开。已知案例：LocalDB故障时journal无任何警告，证据只在该侧车日志。

**J16（P1）重复块没有折叠。** 同指纹块在列表中逐条出现（插件冲突551行、栏杆警告带"- 2 times"后缀）。建议列表按指纹折叠并显示计数，展开后仍可逐条看原文；`scan`已有分组逻辑可复用。

**J17（P2）缺少面向支持工单的导出。** 建议`revit-journal report <journal>`输出Markdown：SHA-256、编码、会话摘要、关键发现（含行号与原文）、侧车清单、未验证声明；与RevitLocalDbFix报告格式对齐，便于一起贴进Autodesk工单。

### D. Windows与测试

**J18（P0）两项测试在Windows失败。** `tests/test_viewer.py:133`：本机系统代理（`127.0.0.1:10808`）被urllib自动使用并改写`Host`，伪造Host的请求被放行；服务端直连时正确返回403。改为`urllib.request.build_opener(urllib.request.ProxyHandler({}))`或`http.client`直连。`tests/test_loading.py:166`：`with sqlite3.connect(...)`只提交不关闭，Windows无法删除仍打开的临时文件；用`contextlib.closing`或显式`close()`。程序代码（`viewer_index.py:95-103`）已正确关闭连接。

**J20（P1）TUI未在原生Windows验收。** `terminal.py:60-89`的控制台模式切换、`\x1b[?1049h`备用屏在Windows Terminal可用，旧conhost需实测；失败时应给出明确提示并回退到`--print`。本次只验证了非交互`--print`路径在Windows正常。

**J21（P2）没有Windows分发形态。** 建议zipapp或PyInstaller单文件，并在README给出`py -m`与真实Journal路径的Windows示例；`README`主示例仍以`--encoding cp1252`开头，对中文用户是误导。

**J23（P2）**规则正则没有复杂度限制（文档已声明）。建议加载时拒绝明显的嵌套量词模式，或在`match`前先用`gate`降低暴露面；`max_line_chars`已限制单行长度。

### 与RevitLocalDbFix的协作

两个项目面对同一批用户。建议：
- 维护一份共享的"Revit已知标记清单"JSON（许可、LocalDB/钢连接、模型打开失败、崩溃特征），本项目作为规则加载，RevitLocalDbFix用C#做简单匹配，避免两边各自硬编码。
- 本项目命中`revit.steel_localdb`或发现`DatabaseConnectionErrors.log`新记录时，在说明中指向RevitLocalDbFix（独立修复工具，不是插件）。

## 附录A：测量方法

执行者可据此重建脚本（脚本用纯ASCII，放在仓库外或`scripts/`并不入库真实数据）：

1. 文件普查：遍历`%LOCALAPPDATA%\Autodesk\Revit\Autodesk Revit *\Journals`，对每个文件尝试`bytes.decode("utf-8")`、`decode(locale.getpreferredencoding(False))`、`decode("gb18030")`，统计行数、高位字节数、尾部是否含`finished recording journal file`。

3. 标记普查：对56个主Journal按gb18030解码后用正则统计2.2表中的标记。
4. 原型A/B：加载`load_rules()`，对同一文件比较"每行跑全部规则"与"门控后再跑规则"的耗时与命中集合。

## 附录B：内置规则的门控建议（J5）

门控为小写子串，任一命中即运行该规则的正则：

| 规则 | gate |
| --- | --- |
| `revit.dbg_error` | `dbg_error` |
| `revit.dbg_warn` | `dbg_warn` |
| `generic.fatal` | `unrecoverable error`、`fatal error`、`unhandled exception`、`access violation`、`无法恢复`、`致命`、`未处理`、`访问冲突` |
| `generic.error_marker` | `error`、`错误` |
| `revit.api_error` | `api_error` |
| `generic.exception` | `exception` |
| `revit.exception_event` | `exceptioncode`、`exception occurred`、`system exception in` |
| `revit.assertion` | `assertion failed` |
| `generic.memory` | `out of memory`、`outofmemoryexception`、`e_outofmemory`、`内存不足` |
| `generic.file_access` | `access`、`unauthorizedaccessexception`、`file not found`、`filenotfoundexception`、`could not`、`拒绝访问`、`找不到` |
| `generic.sync` | `failed to synchroni`、`cannot reconcile`、`merge exception`、`file not saved`、`无法同步`、`同步失败` |
| `revit.missing_schema` | `missing esschema` |

以上组合在本机真实文件上验证为命中集合完全一致；新增或修改规则正则时必须同步复核gate，并由测试保证"有gate与无gate的命中集合相同"。
